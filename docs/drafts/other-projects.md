# 추가 프로젝트 설명 초안과 기존 프로젝트 개선 제안

모두 로컬 검토용이다. 기존 DB·수동 작성 설명·공개 상태는 변경하지 않았다. 개발 기간, 개인/팀 구분, 담당 역할과 회고는 관리자 확인 전까지 기존 값을 유지한다. 아래 공개용 문장과 관리자용 조사 메모는 구분한다.

## Focus Hub — 공개 설명 초안

**부제:** 오늘의 실행과 장기 목표를 한 작업 공간으로 연결하는 생산성 PWA

**핵심 소개:** 일정과 할 일을 따로 기록하는 데서 끝나지 않고, 오늘 해야 할 일과 진행 중인 프로젝트·목표·습관을 한 화면에서 확인하는 개인 작업 공간입니다. 계정별 데이터를 저장하는 구조 위에 데스크톱 대시보드와 모바일 탐색 흐름을 나누고, 빠른 추가와 인증·계정 복구 경로를 연결했습니다.

### 프로젝트 소개

Focus Hub는 할 일, 일정, 프로젝트, 목표와 습관을 중심으로 하루의 실행 상태를 살펴보는 웹 애플리케이션입니다. 대시보드는 오늘의 작업·습관·목표, 주간 일정과 진행 중인 프로젝트를 조합하고, 상세 관리 화면에서는 개별 항목을 추가하거나 수정할 수 있습니다. 모바일에서는 같은 내용을 그대로 축소하는 대신 별도의 개요와 빠른 실행, 하단 탐색을 사용합니다.

### 핵심 기능

- **오늘의 작업과 진행 상황:** 할 일·목표·습관·일정·프로젝트를 대시보드에서 함께 조회해, 기록한 정보와 오늘의 실행 상태를 연결합니다.
- **프로젝트에 연결되는 할 일:** 상태·우선순위·분류·마감일·프로젝트를 입력받고, 화면에서 검색·필터링·수정을 이어갈 수 있습니다.
- **습관과 일정 보기:** 주간 캘린더와 월간 습관 트래커를 분리해, 일정의 시간 흐름과 반복 활동의 누적 상태를 각각 표현합니다.
- **계정 생성과 복구:** 회원가입, 이메일 확인·재전송, 비밀번호 재설정을 독립된 화면과 인증 경로로 구성했습니다.
- **화면 크기에 맞춘 탐색:** 데스크톱 사이드바와 모바일 하단 탐색, 빠른 추가 모달을 공통 AppShell에 연결했습니다.
- **범위를 제한한 PWA 캐시:** 공개 정적 이미지·아이콘은 캐시하되 인증·API·문서·Next 번들 요청은 서비스 워커가 가로채지 않도록 분리했습니다.

### 기술 구조와 핵심 구현

Next.js의 서버 대시보드가 인증 상태와 계정 데이터를 조회하고, 각 관리 화면의 클라이언트 컴포넌트가 입력·필터·모달 같은 상호작용을 담당합니다. Supabase 클라이언트는 서버와 브라우저 용도를 나누며, DB 스키마에는 사용자 범위를 제한하는 RLS 정책이 정의되어 있습니다. 정책의 존재와 실제 운영 환경의 적용 상태는 별도로 확인해야 합니다.

할 일 입력은 React Hook Form과 Zod로 형식과 상태 값을 검사하고, 저장 이후 목록과 피드백을 갱신합니다. 레이아웃은 인증 화면과 작업 공간을 구분하며, 로그아웃 중 중복 실행과 실패 메시지도 처리합니다. 빠른 추가 모달은 필요한 시점에 불러오도록 분리했습니다.

서비스 워커의 캐시 범위는 사용자 데이터까지 오프라인으로 보장하는 구조가 아닙니다. 인증과 서버 응답, 앱 번들은 각 계층의 갱신 정책을 따르게 하고 공개 정적 자원만 별도로 다룹니다.

### 개발 결과와 남은 과제

개별 생산성 기능을 대시보드·관리 화면·모바일 탐색·계정 흐름으로 연결한 구현을 확인했습니다. 인증, 접근성, 캐시와 반응형 화면을 검사하는 브라우저 테스트 코드도 있습니다. 이번 조사에서는 이 저장소의 테스트를 실행하지 않았으므로 통과 수나 실제 운영 안정성을 성과로 추가하지 않습니다.

실제 이메일 발송, 운영 RLS와 계정 간 데이터 격리는 운영 환경에서 확인할 과제입니다. 성능 계측 코드가 있다는 사실만으로 응답 시간 개선 수치를 작성하지 않습니다.

### 담당 역할·기획 배경·Problem Solving·회고

관리자 확인 대기. 코드와 최근 커밋만으로 개인적 동기, 직접 담당 범위와 실패 당시의 원인 분석 과정을 모두 확정하지 않았다. Problem Solving은 비워 두며, 캐시 범위와 인증 경로를 분리한 판단의 배경을 확인한 뒤 사례로 발전시킬 수 있다.

## Developer Portfolio — 공개 설명 초안

**부제:** 저장소의 변경을 근거 있는 프로젝트 설명과 관리자 검토 흐름으로 연결하는 포트폴리오

**핵심 소개:** 프로젝트를 보여 주는 공개 화면과 내용을 검토·관리하는 작업 공간을 분리한 개발자 포트폴리오입니다. GitHub에서 수집한 자료로 설명을 제안하되, 실제 방문자에게는 승인된 DB 스냅샷을 제공하고 직접 수정한 항목은 이후 자동 생성으로 덮어쓰지 않도록 관리합니다.

### 프로젝트 소개

프로필·기술·프로젝트·문제 해결 사례를 재사용 가능한 컴포넌트로 구성하고, 프로젝트의 변화가 설명에 반영되는 과정을 별도의 관리 흐름으로 다룹니다. 저장소 수집, 분석 요청, 관리자 검토와 공개 반영을 연결하면서 외부 API 실패가 기존 게시 내용을 바꾸지 않도록 경계를 나눴습니다.

### 핵심 기능

- **데이터 중심 공개 화면:** 프로젝트 목록과 상세 화면, 홈 Problem Solving을 공통 데이터와 스냅샷 조회로 연결합니다.
- **GitHub 변경 수집:** 저장소 ID와 커밋·소스 manifest를 기준으로 분석할 변경을 찾고, 작업 큐에서 처리합니다.
- **코드에 근거한 설명 제안:** 선별한 파일과 이력을 구조화된 응답으로 분석하고, 실제 제공한 근거를 참조하는지 검사합니다.
- **관리자 검토와 수동 보호:** 현재 내용과 제안을 비교하고, 승인·거절·편집·이미지 업로드·공개 상태 변경을 수행합니다.
- **비용과 재시도 관리:** 요청 전에 예산을 예약하고, 사용량·실패 상태·재시도를 기록합니다.
- **방문자와 생성 작업의 분리:** 공개 페이지 요청에서 GitHub/OpenAI를 호출하지 않고, 승인된 스냅샷만 조회합니다.

### 기술 구조와 핵심 구현

Next.js App Router의 서버 조회 계층은 공개 스냅샷을 읽고, 관리자 API는 세션과 Origin을 확인한 뒤 변경을 처리합니다. 수집과 분석은 DB 작업 큐에 기록하며 lease·중복 키·재시도 횟수로 실행 상태를 관리합니다. 프로젝트 수정과 공개 스냅샷 변경은 같은 트랜잭션에 반영합니다.

AI 제안은 기존 Project 구조에 병합하되 수동 보호 필드를 복원합니다. 같은 커밋과 의미 있는 소스 변경을 비교해 불필요한 분석을 줄이며, 응답을 확인할 수 없는 외부 호출도 비용 예약을 유지합니다. 이미지 업로드는 파일 형식·크기를 검사하고 공개 프로젝트에서 참조하는지 확인합니다.

### 개발 결과와 남은 과제

공개 UI, 기존 데이터, 수집·분석·검토와 공개 반영을 연결한 구현과 격리 DB·Mock·브라우저 테스트 구조를 확인했습니다. 실제 운영의 동시성·API 비용·설명 품질은 Mock 검사와 구분해 검증해야 합니다.

이번 작업에서 추가한 ‘기술 사실 분석 → 상세 글쓰기 → 초안 버전 → 승인’ 구조는 아직 배포하지 않았습니다. 위 공개 설명에 운영 완료 기능으로 섞지 않았으며, 실제 반영 후 별도 성과로 추가할 수 있습니다.

### 담당 역할·기획 배경·Problem Solving·회고

관리자 확인 대기. 기존 분석의 근거 불일치와 파일 선별 문제는 이번 로컬 개선 보고서에 기록했지만, 배포·운영 완료 성과로 먼저 게시하지 않는다. 개인적 회고는 직접 확인한 뒤 작성한다.

## 기존 프로젝트 3개 — 교체하지 않는 개선 제안

### Voyager Atelier

현재 강점은 팀 전체 기능과 본인 담당 범위를 분리하고, 캐릭터 기준점 문제와 폰트 최적화를 구체적으로 설명한 점이다. 기존 설명과 수치는 유지한다.

- 소개 수정안: “React의 정보 UI와 Phaser의 실시간 게임 화면을 연결한 몬스터 수집 JRPG입니다. 베이스캠프·탐험·전투·제작을 하나의 진행 상태로 연결하며, 담당 범위인 플레이어 표현과 주요 게임 화면은 기존 이동·충돌·Scene 구조 안에서 개선했습니다.”
- 결과 항목에는 본인이 맡은 렌더링·엔딩·폰트 작업을 먼저 두고, 팀 전체의 인증·저장 기능은 아키텍처 설명으로 유지한다.
- 폰트 수치는 [9bd49eb](https://github.com/peeta0126/monster-rpg/commit/9bd49eb8535b8513ea2fd7ed2b7a795f1410caf3)의 실제 측정 기록에서 1,207KB → 65KB를 확인했다. 최신 HEAD에서 `design/PERF.md`가 조회되지 않으므로 이 과거 커밋에 고정된 근거를 연결하는 편이 검토하기 쉽다. 이 수치를 이번에 재측정한 것으로 표현하지 않는다.
- 현재 코드 `src/shared/playerSprite.ts`와 기존 이미지 리소스를 재사용할 수 있다. 팀원의 전투·백엔드 변경을 개인 기여로 추가하지 않는다.

### 별빛 타로

현재 강점은 서버 원본 데이터, 입력 분류와 구조화된 AI 응답의 역할이 분명한 점이다. 이번에는 연결된 GitHub 권한으로 비공개 저장소를 읽었으며, 접근한 코드나 비밀값을 공개 자료로 복사하지 않는다.

- 소개 수정안: “사용자가 선택한 카드와 질문을 서버의 원본 데이터에 맞춰 해석하는 AI 타로 서비스입니다. 카드 선택의 인터랙션과 자연어 해석을 연결하면서, 입력 범위와 응답 구조를 서버에서 검증해 화면이 예측 가능한 데이터를 받도록 구성했습니다.”
- 78장·5개 분야 같은 데이터 범위는 한곳에 모으고, 핵심 구현에서는 입력 검증·서버 데이터 재조회·구조화 응답이 각각 막는 오류를 연결해 설명한다.
- `lib/tarotReadingSchema.ts`, API 경로와 `tests/concernIsolation.test.ts`에서 현재 구조를 확인했다. 최근 리포트·PNG/PDF 기능은 커밋에 있으나 개인 담당 범위와 실제 완성도를 확인한 뒤 별도 제안으로 추가한다.
- 기존 Problem Solving과 수동 회고는 교체하지 않는다.

### CrewSpace

현재 저장소는 React 상태와 커스텀 훅으로 회원·신청·일정 UI를 나눈 구조다. README는 Vite 템플릿이어서 제품 설명의 근거로 사용하기 어렵다.

- 소개 수정안: “회원 정보와 가입 신청, 일정 운영을 하나의 화면 흐름으로 연결한 동아리 관리 UI입니다. 신청 검증과 승인, 회원 목록 반영을 기능별 훅으로 나눠 관리하며 관리자 화면에서 가능한 동작과 일반 사용자 흐름을 구분했습니다.”
- `src/hooks/useCrewSpaceState.ts`가 승인·회원 반영과 관리자 UI 조건을 조율하고, `useAuth.ts`가 입력 검증을 처리하는 점을 설명한다.
- 클라이언트의 관리자 조건 검사를 운영 서버의 권한 검증이나 안전한 인증 시스템으로 확대하지 않는다. 현재 저장소에서 백엔드·운영 DB는 확인되지 않았다.
- 개인 역할, 실제 사용자 운영 성과와 테스트 실행 결과는 관리자 확인 전까지 추가하지 않는다. 기존 설명은 그대로 보존한다.
